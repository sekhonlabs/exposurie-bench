# Decisions

Dated, newest last. Each entry says what was decided and why.

## 2026-10-18

- **A separate public repository.** The method and the results can be checked and rerun, and cloud sessions can work on it. The repository, the run sandbox and the raw outputs share one folder on a disk kept apart from the owner's personal setup. The sandbox and raw outputs never enter the repository.
- **Runs use a Claude plan login, never an API key,** because of cost. As a result there is no `--bare` mode, which only accepts API keys. Isolation comes from a separate home folder and `CLAUDE_CONFIG_DIR` instead.
- **Claude Code builds and runs everything.**
- **Synthetic users, not real people's histories.** Their right answers are known, they contain no private data, and anyone can rerun them.
- **One agent, Claude Code.** There is no second-agent arm.
- **Broad, not deep.** The benchmark has nine areas, three tasks in each, and one run per cell, about 105 runs in total. An earlier draft had 2 users × 20 tasks × 4 conditions × 3 runs = 480.
- **The half-context-window rule of thumb gets tested rather than asserted** (area 9).
- **The two users are a great developer and someone who hands everything to agents** and just wants the work done. Neither is tied to a niche job or industry.
- **Cloud sessions are an option, not yet the plan.** It is unverified whether nested `claude -p` runs work inside a cloud machine.
- **Model: Sonnet 5.5 (`claude-sonnet-5-5`).** It is pinned for every run, both brain builds, the generated histories and the judge, so one model is used throughout.
- **About 80K tokens of conversation per user.** Real histories run past any context window, which would make B impossible to run. This size keeps B runnable while staying far too long to paste into every session. The pilot confirms that B fits with room for the task.
- **The four conditions differ by one file:** the sandbox's global instructions file, which is where exposurie puts its pointer. Using one mechanism for all four keeps the comparison fair.
- **The sandbox has its own pinned Claude Code and exposurie, with auto-update off.** Claude Code went through 44 version numbers in the 46 days before this decision, and the run takes several days.
- **Sonnet 5.5 writes the histories from written session plans, inside the sandbox, without session persistence.** The plans control where every fact appears. The sandbox keeps the owner's setup out of the text. Without persistence, the generation sessions themselves never end up in the history. The generated text is committed, and it is what every run uses.
- **More run-hygiene rules**, each guarding against a specific wrong number:
  - transcript retention is set before any history is placed
  - claude.ai connectors and auto-memory are off
  - every run gets the same tool list, checked at the start
  - the raw history is removed after the brain build
  - C runs finish within 7 days of the build
  - every input token is counted, cached or not
  - conditions are mixed together in the run order
  - a run stopped by a usage limit counts as not run

  Details are in design.md.
- **An answer with both a required and a forbidden fact goes to the judge and the hand check**, because a correct answer can name the old choice while giving the new one.
- **Area 9 is built last**, once the pilot shows how much plan usage the run needs. It needs sessions to be saved, and that exception is decided when it is built.
- **Charts and write-ups use exposurie's own look** (see CLAUDE.md).
- **The build follows docs/build-plan.md, one part at a time:** each part is discussed, built and checked before the next one starts.
- **Everything the benchmark installs, writes or runs stays in its own folder:** this repository, `../sandbox` and `../runs`. Nothing of the owner's own setup is read or written. So the sandbox carries its own Node and Git as well as Claude Code and exposurie, each pinned and checked against its published hash.
- **The run environment is built, never inherited:** Windows' own variables plus the sandbox's paths. A run is often started from inside another agent session, and that session's variables (its effort setting, its session ID) would otherwise reach the run.
- **Remote feature flags are off** (`DISABLE_GROWTHBOOK=1`). There are two reasons:
  - On Windows, one flag (`tengu_windows_credman`) moves the login out of the sandbox's credentials file and into the Windows user's Credential Manager, which is outside the sandbox.
  - Any flag can change behaviour partway through the run.

  So every run gets the pinned binary's own defaults, the same on every day and for anyone who reruns the benchmark.
- **The binary's built-in plugins and skills stay on.** Claude Code 2.1.302 ships three plugins (`cc-plugin-agents-md`, `cc-plugin-telemetry` and `cc-plugin-plugin-authoring`) and 17 skills of its own. They come with the pinned version and are the same in every condition.
- **The login happens in the owner's own browser**, by copying the sign-in URL from the sandbox's Claude Code. A browser started from the sandbox creates a new profile inside it. On the first try, Edge signed that profile in with the owner's account and synced into it, and the profile was then deleted. `sandbox.mjs check` now fails if anything but `.claude` and the empty `AppData` folders appears in the sandbox home.
- **The developer also has a job**, at the owner's suggestion: a developer at a company works across its repositories, with connectors and memories of their own, and a brain can carry that working life too. So the developer works at a made-up company, Tidewell, as well as on four projects of their own: 28 sessions across 6 repositories, instead of about 25 across about 4.
  - Connectors stay off in every run, and exposurie drops what a connector returns. So where a connector would act, a task writes a file instead.
  - The team's rules and the developer's own disagree in places, and some tasks check that neither leaks into the other.
- **The users have no names.** Real users rarely tell Claude Code their name. Their folders are `users/developer` and `users/delegator`.

## 2026-10-20

- **The fact sheets carry more than the build plan first listed.** For each fact they also give its kind, its context (work or personal), how it first comes up (said by the user, proposed by the agent and accepted, or a correction), the options turned down and the session that names them, and the tasks where stating it would be wrong. A rival choice may be named only where a fact or a turned-down option plans it. Each user also lists what is never discussed, with the words that must never appear. See build-plan.md, part 1.
- **The sessions are fixed in part 1**, in `users/<user>/plan.json`: each one's time, project or chat, and surface. A fact's first session means nothing without them. Part 2 adds how each fact comes up.
- **The task list starts in part 1**, in `tasks/index.json`, so the fact sheets can point at tasks. Part 4 completes each task.
- **"Non-default" applies to the facts a task asks about.** The other facts also include people, places and habits, as a real history does. A replaced value may be a popular default, since it is never the right answer.
- **26 tasks, not 27:** three in each of areas 1–8, and two in area 9.
- **`check/facts.mjs` holds both fact sheets to the method** before any history exists. Part 3's history checker reads text the same way, with its `mentions` rule.
- **The owner approved both users' fact sheets**, which ends part 1.
- **Each session is generated from a written brief**, kept in `plan.json`. It says what happens, how each fact first said in the session comes up, which earlier facts come up again, and how long the session is. The prompt is built from the brief, the fact sheet and the checker's rules, so the prompt and the checker cannot disagree.
- **Generation runs the sandbox's Claude Code with the brief as its whole system prompt,** with no tools, skills or MCP servers. Writing text needs none of them, and leaving them out keeps every attempt small. A session is checked before it is kept. One that fails is written again with the checker's findings, up to three times.
- **The assistant in the histories remembers nothing between sessions**, as Claude Code doesn't. An earlier decision reaches a later session only when the user says it again or the agent finds it in the code. That is the gap a brain is built to close.
- **The transcripts carry conversation only, with no tool calls.** exposurie 1.2.0 keeps only the text blocks of user and assistant lines (`src/extract/transcript.js`), so tool calls and their output would change nothing it reads. Leaving them out also means no fact can sit in a tool call where the checker would miss it. Connector calls at work are left out the same way, and what a connector did is said in words.
- **The claude.ai export carries the chats and an account file with no name in it.** A real export may also carry claude.ai's own memory of the person (`memories.json`) and the instructions of their claude.ai Projects, and exposurie reads both ahead of the chats. They are left out because here they would be a summary written by us, not by claude.ai, and only C would read it. The second user's chats are not in a claude.ai Project.
- **The transcripts record made-up working folders on macOS**, such as `/Users/dev/code/satchel`. Each ends in the project's name, because exposurie names a project after its folder. The account names in them are placeholders, since the users have no names.
- **The converted files are not committed.** Git does not keep file dates, and exposurie orders history by them. The converter is deterministic, and part 6 converts straight into the sandbox home. The sessions are committed, and they are what every run uses.
- **"No other choice of the same kind" is checked against a list of names**, `check/rivals.json`, plus every turned-down option. Names that are also ordinary words are matched by their case or left out. So are names used everywhere (npm, Node, git, GitHub, VS Code), because a whole-word match cannot tell a choice from a word.
- **Where a chat would naturally offer several options**, such as names, places, gifts or subject lines, it offers one. Any other option would be a rival nobody planned.
- **Every transcript line records the pinned Claude Code version**, 2.1.302, rather than a version history made up for the dates.
- **Each session's length follows the history's budget, not only its brief.** The pilot's sessions came in short, so the prompt asked for at least the planned length. The first eleven developer sessions then came in at 1.39 times it, which would have put that history near 114K tokens. So each new session is asked for its share of what is left of the 80K: the tokens the written sessions have not used, spread over the briefs still to write. The share is kept between 0.7 and 1.6 of its brief, and `generation.json` records it. The upper end was 1.3 at first. But the second user's desktop sessions came in at about 0.6 of what they were asked for, because a person who types a few words gets short replies. Their claude.ai chats keep close to what they are asked, so they carry the length the desktop sessions cannot. The method's number is unchanged: about 80K tokens of conversation per user.
- **A heading inside a code block is allowed.** Every heading the checker refused in the first run was part of a document the assistant was showing, such as a README or a pull request description. Outside code blocks, turns still never start a line with `#` or `##`, the marks that separate turns in a session file.
- **del-04 is written again.** Its kept draft had the assistant say the user writes late at night, which only a claude.ai chat had said. The pilot found it, and the prompt was fixed, but the draft was kept. It is set aside like dev-01, and its draft stays in `../runs`.
- **The assistant knows a team's conventions only once they are said.** Reading the developer's history found five sessions where the assistant used something said only in an earlier session: the team's pull request sections, its two approvals and squash merges, where its handbook lives, and once "You said to ask before adding any dependency". The prompt already said the assistant knows nothing about the person beyond the files. It now says the same of the team's conventions, and that the assistant asks until it is told. The pull request sections are a fact a task asks about, so the extra mentions would also have favoured B and C. dev-11, dev-15, dev-18, dev-23 and dev-27 are written again, and their drafts stay in `../runs`.
- **The sandbox login's own email address and names never appear in a session.** Claude Code 2.1.302 adds the logged-in account's email address to every run's context (its user context `userEmail`, taken from the account), even when the run brings its own system prompt. Only `ANTHROPIC_UNIX_SOCKET` turns it off, and that changes how Claude Code connects. One developer session used the address as a blog's contact address, and was set aside before it was committed. The checker now refuses the login's address and names. It reads them from the sandbox when it runs, so they never enter the repository, and its findings never quote them. The prompt says every address is made up, at example.com.
- **The same address reaches every benchmark run**, in all four conditions alike. It changes no condition against another. But a run can write it into a file, so parts 5 and 6 hold everything they save into the repository to the same check.
- **Area 5 is judged, like area 4.** Its answers are advice, and advice is right only when it follows the user's decision for the user's reason. A list of spellings cannot tell those apart. A fresh agent can say "no" to Drizzle for a generic reason, while an agent that knows the user can put their rule many ways ("you keep ORMs out of your own code"). The spellings would pass the first and fail the second. Each area 5 task has a fixed rubric, and every answer is also checked by hand.
- **Area 7 reads the agent's reply as well as its files.** It measures whether a plan made in claude.ai reaches the coding agent. An agent may write the welcome email into its reply rather than a file, or keep the vote's closing time in code as an hour while it names "20:00" in the reply. Either way, the plan reached it. Area 6 reads only the files, because it measures whether the work is done the user's way.
- **Checks read text the way agents write it.** Backticks are removed, as part 3 found that "`.sql` files" is not ".sql files", and curly quotes are straightened. An HTML page is read without its markup, so a doctype or a script's "!" is not an exclamation mark. `score/checks.mjs` holds these rules for the task check now and the scorer in part 5.
- **Questions run in an empty folder named `scratch`**, so the folder's name points at no project. Work tasks run in a folder with the project's own name, as the user's would be.
- **Each starter is the project as its last session leaves it.** The sessions were written without memory of each other, so a few disagree: book-club's page is `Index.html` in some sessions and `index.html` in others, and spending-summary's script is `summarise.py` until its last session calls it `summary.py`. That last session also says the summary is pasted into the Sheet by hand, where an earlier one had the script send it. Where sessions disagree, the latest wins.
- **real-work-1 is a new app of the developer's own**, because Satchel already has its deploy files. It is written their way: Hono and htmx, SQLite with its queries in `.sql` files, Biome, node:test, pnpm and Node 24.
- **real-work-2's bug comes from a later change.** dev-20's own tests covered an organisation with no projects in the export service. So the starter's route also sets a Last-Modified header from an aggregate, which is null when there are no projects. That makes the endpoint fail with a 500.
- **real-work-2's question no longer starts "ENG-431: …"**, since that is the title convention the task asks about.
- **B's file is the history as exposurie reads it**, oldest first: only what was said. Each session is headed by what exposurie also knows about it: its start, its surface, and the folder it ran in or the chat's title. Git branches stay out, because exposurie does not read them.
- **D's file is notes, one line per fact:** where the fact applies, its kind, its value and its reason. It carries only what the task needs, and nothing marks a fact as current or replaced.
- **The condition files are committed**, so what each condition was given can be read. `check/tasks.mjs` fails when one differs from what `tasks/conditions.mjs` writes.
- **C differs from A by more than the instructions file.** exposurie's setup also writes its skill (`~/.claude/skills/exposurie/SKILL.md`) and its `/exposurie-sync` command into the sandbox's Claude Code folder. They come with exposurie, so they are part of condition C. design.md now says so.
- **Area 8's questions carry their own inputs**, the regular expression and the CSV. Their checks only confirm the work was done, since area 8 measures tokens.
- **Every task scored by its checks has examples**, in `tasks/examples.json`: a right answer and a wrong one, and some that must go to the judge. The task check scores each one, so a spelling or pattern that would misread an answer fails before anything runs.

## 2026-10-21

- **The `exposurie` command is on the PATH only in C.** design.md counts the command among what exposurie installs, so A, B and D run with the sandbox's npm folder left off the PATH. That folder holds only the `claude` and `exposurie` command shims, and runs start Claude Code by its full path.
- **Edits are accepted inside the run's own folder (`--permission-mode acceptEdits`), and nothing else is.** A work task has to write files. Anything else that would ask for permission is denied, since nobody is there to answer, and the shell may still run only `exposurie`.
- **Every tool call is held to the run's folder.** The runs sit beside this repository, which holds the answer key, and beside each other's answers. So the runner reads every tool call in the output stream. A run is thrown out if it reached a file outside its folder or ran a shell command other than `exposurie`. C may also reach its brain. A call that was denied reached nothing, so it is only noted. The first real runs show whether a headless run is denied reads outside its folder, as expected.
- **A run's answer is its final reply**, the text the run's result line carries. The text written before tool calls is left out, because "let me check whether you still use Vitest" would trip a forbidden check on an answer that ends up right.
- **Run IDs say nothing about the run.** The agent sees its folder's path, so a run's folder is `../runs/<batch>/r017/<folder>`, numbered in run order. Which task and condition a run had is kept in the batch's `batch.json`, and the scorer reads only the run's own folder: its task, its final reply and the files it created or changed.
- **The order is mixed by a hash:** cells are sorted on a hash of the seed and the cell, so the same seed always gives the same order.
- **Each run gets its condition placed in the sandbox home, and taken out after.** For C that is a fresh copy of everything exposurie installed and of the brain, from `../sandbox/brains/<user>/`, so every C run starts from the same brain. A run that changes any file of its condition is thrown out. `keep-brain` moves the brain there after the build, and the raw history with it.
- **C runs only on a brain synced in the last 7 days with nothing left unfiled.** That is exposurie 1.2.0's own rule for when its status line asks the agent to sync (`unfiled > 0 || lastSyncDays >= 7`).
- **Tokens are counted over every model a run used** (`modelUsage`), since Claude Code can call a smaller model alongside the pinned one.
- **How a run can end.** A run stopped by a usage limit, an API error, a crash or 30 minutes without a result is "not run", and the next `go` runs it again. A usage limit also stops the batch, and so do three API errors in a row. A run that breaks a hygiene check is thrown out, and runs again only when asked for by name, once the cause is fixed. There is no turn cap: 2.1.302's help lists no `--max-turns`, and a cap is a rule real users do not have.
- **The judge is a separate run** with the pinned model and no tools, in an empty folder and a sandbox home holding no condition. It is given the question, the rubric, the final reply and the files, and it answers in two lines, `VERDICT:` and `REASON:`. Every judged run is listed for the hand check, and a hand verdict is final.
- **One sandbox process at a time, enforced.** A lock file in the sandbox holds the owner's process ID. The runner, the judge, `sandbox.mjs check` and `login` all take it.
- **The sandbox sets `USERNAME`, `USERDOMAIN` and `LOGONSERVER` itself.** Windows gives a child process its parent's values whenever its environment leaves them out (Node's libuv counts them as required), so every sandbox process since part 0 had carried the machine owner's account name. No model could have read them: generation had no tools, and part 0's check could run only `exposurie`. The fake `claude` found it, by refusing any variable that `sandboxEnv` does not set.
- **No instructions file may sit above the runs.** Claude Code loads `CLAUDE.md` from every folder above the one it runs in, and it ships a built-in plugin for `AGENTS.md`, so such a file would reach every run in every condition. None does (checked 2026-10-21). The runner and the judge refuse to start if one appears.
- **A large instructions file gets a warning, not a cut.** Claude Code 2.1.302 warns when an instructions file passes the larger of 40,000 characters and 5% of the context window, and loads it whole. B's files are about 339K and 304K characters. The pilot still checks B's input tokens, as design.md says.
- **The runner and the scorer are tested against a fake `claude`** that prints output in the real format, read off part 0's run and part 2's usage-limit stop. It checks what each run was handed. A fault test that broke the code fifteen ways was caught every time.
- **A brain is built the way a person's agent would build it, headless:** Claude Code types exposurie's own `/exposurie-sync`, with a run's model, tools and permission mode, until exposurie's state says nothing is staged or waiting. If one session stops early, another starts, and the build's tokens are summed over every session.
- **The build runs in the brain's folder.** Edits are accepted only inside a run's own folder, and nobody is there to approve one anywhere else. Claude Code therefore also loads the brain's own `CLAUDE.md` at the start. That file is exposurie's schema, which the scaffold's own plan tells an agent to read anyway.
- **`exposurie scaffold` runs without a model.** It is deterministic, so the runner runs it. A real first setup also pays the few thousand tokens an agent spends running it and reading its output, and the build's count leaves those out.
- **exposurie's steps for the person are settled before the build.** Transcript retention is already set by the sandbox's settings, and exposurie detects that. The claude.ai export and Obsidian are declined, with no reason recorded, because nobody gave one: the synthetic users can't be asked, and either step left open would be written into the brain by any later sync. For the second user the export is in Downloads during the build, and exposurie reads it there; it leaves with the history.
- **The staged batches leave the brain with the raw history.** After a batch is filed, exposurie 1.2.0 keeps it in `.exposurie/staged/`. It is the conversation itself, as exposurie hands it to the agent, and exposurie's own `.gitignore` for a brain calls that folder machine state, not content. Left in place, C could search its way to B's material through its own brain folder. `keep-brain` moves it out with the history.
- **A build session is checked like a run.** The brain may be written, and the history and the export read. Anything else outside the brain, or any shell command but `exposurie`, stops the build until a person has read the session. Their decision is written into the build's record with `--accept "<why>"`, or the build starts again. The answer key sits one folder over, and a brain built with it would make C's results worthless.
- **A probe answers what the fake can't.** One small run, set up as condition A, is asked to read a file one folder above its own and to run `ls` and `git status`. It shows whether Claude Code denies a headless run's read outside its folder, and whether it lets any shell command through without asking. The audit would throw such a run out.
- **What the probe found.** In a headless run, Claude Code 2.1.302 denies a read outside the run's folder, with the Read tool and with the shell (`cat ../outside.txt`, `ls ..`). Inside the folder it lets read-only commands (`ls`, `git status`) run without asking, though only `exposurie` is allowed. The first probe asked three of these things, and the second all five.
- **So a shell command Claude Code allows by itself is noted, not thrown out.** An agent reaches for `ls` in every condition, and throwing out each run that did would waste runs and favour whichever condition looks around least. Claude Code keeps these commands inside the folder, which is what the rule was for. The audit still throws out any shell command that names a place outside the folder, as a backstop, and design.md describes the shell this way.
- **In a headless run, C reaches its brain through `exposurie read`.** A brain page is outside the run's folder, so Claude Code denies a direct read of it, where a person at the keyboard could approve one. `exposurie read` is the librarian exposurie points an agent to, and it returns the pages. design.md lists this under *Limits*.
- **The audit reads a here-document as text, not as commands.** The developer's build appended to its log with `cat >> log.md <<'EOF'`, and a backtick in that text read as a command of its own, which stopped the build on a false flag. The runner now skips here-document bodies, and `check/build.mjs` holds it to that. Re-audited, the session had no problems, and every one of its file tool calls stayed in the brain. The build's record keeps the flag and the decision to accept it.
- **The histories are larger in real tokens than planned, and nothing changes for it.** They were sized at 4 characters per token. The pilot's B run measured Sonnet 5.5's own count: B's input less D's is about 119K tokens for the developer's 338,692-character history file, about 2.85 characters a token, so about 1.4 times the 80K planned. B still fits with room, since the model's window in Claude Code 2.1.302 is 1,000,000 tokens. The histories stay as written and checked, and design.md gives both counts.
- **The pilot task is recall-1**, a plain recall question for the developer. Most of the 24 tasks are questions, its answer is scored by its checks, and it needs the user's past in every condition but A. The probe covers the shell and the folder, which a question may never touch.
- **The full run repeats the pilot's task.** The pilot ran recall-1's four runs in a fixed order, A to D. The full batch plans all 24 tasks of areas 1–8 anyway, so the whole run is one batch in one mixed order, on the same brains, and the pilot stays a pilot.
- **The stability check is area 3, fixed before any result was in.** Its three tasks run twice more under C, as the batches `stability-1` and `stability-2`. The design expects curation to lose detail first where a decision changed, so that is where it matters most whether C's answer holds between identical runs. Its answers are scored by checks, so no judge adds variation of its own.
- **The audit reads the null device as no place.** In the full run, an agent ran `cat README.md 2>/dev/null` inside its folder, which Claude Code let through by itself, and the audit read `/dev/null` as a place outside the folder and threw the run out. The runner now skips the null device and the standard streams, and reads `&>` as a redirect, as it reads `>`. `check/build.mjs` holds it to that. Re-audited with the fix, the batch's other 29 runs came out as they were saved. The run thrown out is run again by name, as every thrown-out run is, and its first attempt is kept beside it.
- **The hand check overturned two of the judge's 43 verdicts, both to right.** It was done blind: every verdict was written before anything naming a condition was opened.
  - **your-way-1, `full/r021`.** The reply turns Drizzle down because the user ruled it out for Satchel to keep the SQL in view for `EXPLAIN QUERY PLAN`, with the queries in `.sql` files. The judge wanted the rule in its own words, "no ORMs in their own code". But the fact sheet gives that rule's reason as an ORM hiding the queries the user needs to tune, and this reply gives that reason in other words. The 2026-10-20 entry on area 5 says a user's rule can be put many ways.
  - **your-way-3, `full/r083`.** The reply says no to logins because the club code already does the job and members won't use accounts, which is the settled reason. The judge counted its fallback for a disputed vote, a short code for each member, as recommending a login. The reply says "don't add logins", and offers the code only "if the vote ever causes a dispute". The judge passed two other answers with a similar fallback: a personal link for each member, and a login for the organiser alone. So all three are held to one standard: a fallback that keeps members without accounts is not a login.
- **Two answers the checks scored right are corrected by hand to wrong.** Both are fresh-session refusals: recall-3's *"I can't tell you which newsletter service you set up"* (`full/r023`) and changed-3's *"I can't tell where your site is hosted"* (`full/r062`). Each lists the services it searched for, the right one among them, and a required check matches a name wherever it stands. They were found after the conditions were opened, while reading why the fresh session had right answers where nothing could be guessed, and they need no judgment: each says it cannot tell. Every other answer the checks settled in areas 1–3 was then read, in all four conditions, and none has this fault. By the checks alone, the fresh session has 5 right answers of 21 in areas 1–7. With the two corrected, it has 3.
- **The stability answers went to the judge after all.** Each one named the old choice beside the new one, and such an answer goes to the judge (2026-10-18). The hand check settled all six, so the judge's own variation reaches none of them.
- **Area 9 interrupts each long session at 500K tokens**, half of Sonnet 5.5's 1,000,000-token window in Claude Code 2.1.302. The owner chose it from three options before anything was built. The other two were a fixed 200K, and auto-compact capped at 200K with the interruption at 100K. 500K is the only one of the three that tests the rule of thumb as it is stated. Each task's session is filled once and forked three ways (`--resume <id> --fork-session`), so the three strategies start from the same point and the fill is paid once. One task runs first, and its measured cost decides whether the second runs.
- **Area 9's sessions are saved: the one exception to run hygiene.** A long session is carried on step by step and forked, which needs its transcript. Every other area keeps `--no-session-persistence`, and so do area 9's sync sessions. After every step the runner moves what Claude Code saved in the history folder into the run's own folder, and puts it back before the next step, so between steps the sandbox home holds nothing of it.
